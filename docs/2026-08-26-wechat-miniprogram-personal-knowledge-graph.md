# 微信「个人知识与人脉图谱」小程序

## 设计框架、可行性分析与建议

> 文档日期：2026-08-26  
> 定位：产品与架构设计备忘，不是可直接开工的实现说明书。  
> 前提：服务对象是用户本人整理自己的注意力与关系；不采集、不还原他人的聊天与浏览。

---

## 0. 结论先讲清楚

原需求的大意是：在微信里做一个「个人操作系统」——按时间段还原用户看过哪些公众号 / 视频号 / 直播、内容属于什么领域、和谁交流过、谈了什么、时间花在哪，再做成知识图谱、人脉网络、人群中的水平分布，以及未来该往哪拓展。

这个价值主张成立，但**不能按「后台静默读取微信全量行为」来做**。

原因不是技术栈不够，而是微信的运行逻辑就是这样设计的：

1. **小程序是微信里的客人，不是微信本身。** 它只能看到自己进程内、且用户明确授权的数据。
2. **会话、关系链、浏览历史、广告曝光，属于腾讯平台核心资产与用户敏感信息。** 官方不开放，运营规范明确禁止收集、抓取或要求用户提供。
3. **《个人信息保护法》把通信内容、行踪轨迹等视为敏感个人信息。** 即便用户「愿意上传聊天记录」，第三方小程序大规模处理仍面临合法性、最小必要、安全与审核四重墙。

因此：

- **原设想的「全自动微信人生仪表盘」：作为小程序不可行，也不应尝试用外挂、无障碍监听、PC 微信 hook、聊天截图上传等方式绕过。**
- **可做成的产品：用户主动投喂的「微信内个人知识与人脉操作系统」。** 采集面变窄，但知识图谱、时间分配（基于已记录样本）、人脉 CRM、匿名分位、拓展建议都可以做，而且能过审、能长期活。

下文把「微信实际给什么」和「产品应改成什么」一次对齐。

---

## 1. 需求还原：用户真正要买的不是日志，是判断力

把原需求拆成五层，避免一上来就绑死在「读取微信后台」。

| 层 | 用户原话 | 真实价值 |
| --- | --- | --- |
| 注意力账本 | 过去一周看了哪些号、哪些内容 | 知道自己的信息饮食是什么 |
| 语义理解 | 财经 / 新闻 / 广告，或更细领域 | 从「看过」变成「懂自己在学什么」 |
| 关系账本 | 和谁交流、沟通什么 | 人脉不是通讯录，是互动与主题 |
| 时间分配 | 时间花在哪 | 注意力预算，而不是手机厂商的屏幕时间 |
| 位置与建议 | 在全部用户中的水平、该往哪拓展 | 比较感 + 下一步行动 |

这五层里，只有「自动、完整、跨公众号 / 视频号 / 直播 / 私聊 / 群聊还原」这一条做不到。其余四层都可以在**用户授权的自有数据**上做。

产品一句话应改成：

> 帮你把愿意留下的阅读、观看和交往，变成一张只属于你的知识图谱和人脉图，每周告诉你：注意力去了哪、关系停在哪、下一步值得补什么。

不要做成「微信使用监控器」。那既过不了审核，用户也不会真正放心把人生数据交给你。

## 2. 微信运行逻辑：为什么客人拿不到主人的日记

### 2.1 微信是三套数据世界叠在一起

```text
┌─────────────────────────────────────────────┐
│  A. 客户端本地：聊天记录、部分草稿、设备侧缓存 │
│     微信隐私政策亦强调聊天记录主要在用户设备端 │
├─────────────────────────────────────────────┤
│  B. 腾讯平台侧：关系链、关注列表、浏览与推荐、  │
│     广告曝光、视频号 / 直播观看、使用时长等     │
├─────────────────────────────────────────────┤
│  C. 开放给开发者的：登录身份、用户明确授权的    │
│     手机号 / 位置等、本小程序内行为、少量跳转   │
│     与分享场景（如群 openGId）                 │
└─────────────────────────────────────────────┘
```

小程序几乎只活在 **C**。原需求要的数据几乎全在 **A 和 B**。

这不是接口暂时没开放，而是商业与合规结构：关系链和内容消费是微信的护城河；一旦开放给任意小程序，就是把社交图谱和注意力图谱交给第三方。平台规则写得很直白——未经腾讯同意，不得收集、存储、抓取、获得或要求用户提供微信侧信息与用户数据，包括用户关系链、好友列表等，也不得用合法拿到的数据去创建、补充自己的关系链。见[《微信小程序运营规范》5.12.14 / 15.2.9](https://developers.weixin.qq.com/miniprogram/product/)。

### 2.2 小程序能做的「官方动作」（与本需求相关）

这些能力存在，但都是**跳转、展示、本应用内记录**，不是「读取用户在微信里做过什么」。

| 能力 | 官方含义 | 对本产品的意义 |
| --- | --- | --- |
| `wx.login` / openid / unionid | 识别本小程序用户 | 账户体系，不是社交图谱 |
| 分享到聊天 / 朋友圈 | 用户主动转发本小程序卡片 | 增长与「从群打开」场景 |
| `wx.getShareInfo` / `getGroupEnterInfo` | 从群卡片进入时可拿到匿名 `openGId` | 知道「来自某个群」，不知道群成员、群名（展示需开放数据组件）、聊天内容 |
| `wx.openOfficialAccountArticle` | 用户点击后打开任意公众号文章 | 适合「回看已保存的链接」，不能列出阅读历史 |
| `wx.openOfficialAccountProfile` | 打开公众号主页（主体 / 版本有限制） | 引导关注**你关联的号**，不是用户关注了哪些号 |
| `official-account` 组件 | 限定场景下引导关注同主体公众号 | 获客，不是扫描关注列表 |
| `wx.openChannelsActivity` / `openChannelsUserProfile` / `channel-video` | 打开或内嵌指定视频号内容 | 你已有视频 ID 才能打开；没有「我看过的视频号」接口 |
| `web-view` | 只能打开已配业务域名，或已关联公众号的文章 | 不能当通用浏览器去爬用户的阅读轨迹 |
| `wx.getClipboardData` | 隐私接口，需用户同意隐私协议 | 用户刚复制了文章链接时，可询问是否入库 |
| 订阅消息 | 用户主动订阅后可发有限模板 | 做「每周回顾」提醒，不能做系统级监控 |
| 本小程序内停留时长 | 自己统计 | 只代表在本产品里的时间 |

客服消息、支付、位置、相册等与本需求主路径关系不大，不展开。

### 2.3 明确不存在、也不要去找的接口

- 用户阅读过的公众号列表、文章列表、停留时长  
- 视频号 / 直播观看历史、完播、点赞、收藏（创作者后台只给**创作者看自己的内容数据**）  
- 朋友圈、搜一搜、看一看、广告曝光与点击  
- 好友列表、通讯录、群成员列表、单聊 / 群聊文本与语音  
- 微信总使用时长、各入口时长（那是微信自己的产品数据，外加系统「屏幕使用时间」）  
- 「该用户在全体微信用户中的百分位」——腾讯不会把全网分布卖给第三方小程序  

创作者侧（公众号后台、视频号助手）能看到的是**你的内容被谁看了**，方向与本需求相反：那是媒体的读者分析，不是读者的自我分析。

### 2.4 三条绝对不要走的路

| 路径 | 为什么看起来香 | 为什么不能做 |
| --- | --- | --- |
| 无障碍 / 悬浮窗 / 读通知监听微信界面 | 能「看见」聊天和订阅号 | 违反平台规则与隐私法，属于未授权获取；账号与应用都会死 |
| PC 微信协议 / hook / 自动化 | 能导出聊天与部分列表 | 灰色产业玩法，不稳定、违法风险高，小程序形态也接不住 |
| 要求用户上传聊天记录或聊天截图再 OCR | 好像是「用户自愿」 | 运营规范禁止要求提供微信侧敏感数据；截图里有对方个人信息；审核与舆情都过不去 |

后文只讨论**合法、可过审、用户可理解**的路径。

## 3. 可行性对照：原功能逐条打分

评分含义：

- **不可行**：官方无接口，且做了会违规  
- **可间接**：必须改交互，用用户主动记录代替系统读取  
- **可行**：在自有数据上可完整交付  

| 原功能 | 判定 | 说明 | 合法替代 |
| --- | --- | --- | --- |
| 统计访问过哪些公众号 | 不可行（自动） | 无阅读历史、无关注列表 API | 用户把文章转发给本小程序、粘贴链接、或「今日读了哪些号」点选 |
| 统计视频号 / 直播 | 不可行（自动） | 只能打开指定内容，不能拉观看历史 | 分享卡片 / 粘贴视频号链接 / 看完后打卡 |
| 内容领域分类（财经、新闻、广告…） | 可间接 | 没有全量语料就无法对「看过的广告」分类；广告曝光完全拿不到 | 对**已入库内容**做标题 / 摘要 / 用户标签的分类；广告单独做成「我主动标记看到的广告」 |
| 更细领域 | 可行（对已入库样本） | NLP / LLM 分类 | 预置行业树 + 用户自定义主题 |
| 与哪些人交流 | 不可行（自动） | 禁止拿关系链 | 人物卡片：用户自己添加；或双方都是本产品用户且互相确认 |
| 沟通什么内容 | 不可行（自动） | 聊天内容不开放，也不应收集 | 「会后三句话」：主题、结论、下一步；用户手写或语音转写**自己的备忘** |
| 时间分配 | 可间接 | 没有微信级屏幕时间 | ① 本小程序 session；② 每条内容的「阅读时长」由用户估或在站内阅读时计时；③ 每晚 30 秒复盘 |
| 知识图谱 | 可行 | 图谱是你自己建的模型 | 实体：内容、来源、主题、人物、事件、时间片 |
| 人脉网络 | 可间接 | 不能画微信好友图 | 画「你记录过的人」；边是互动次数、主题、最近联系 |
| 在全部用户中的水平分布 | 可间接 | 没有全微信统计口径 | 仅在本产品、自愿加入匿名样本的用户中算分位，文案必须写清「本产品用户」而非「全体微信用户」 |
| 未来拓展建议 | 可行 | 依赖图谱质量 | 主题缺口、来源多样性、关系跟进、学习路径 |

一句话：**自动还原微信 = 0 分；主动记录后的洞察 = 高分。**

## 4. 三条产品路径，只推一条主路

### 路径 A：微信行为监控器（原设想）

小程序静默还原阅读、观看、聊天。

- 优点：如果真能做，差异化极强。  
- 缺点：做不到；做了即违规；即使用户同意，腾讯也不同意。  
- 结论：放弃。

### 路径 B：创作者 / 企业的读者与组织图谱（方向相反）

服务公众号、视频号、企业微信管理员：看粉丝结构、内容主题、内部专家网络。

- 优点：数据在官方后台或企业微信开放接口里，B 端付费意愿清楚。  
- 缺点：不是「帮微信用户整理自己」，和原需求主语相反。  
- 结论：可作后续商业化支线，不要冒充本需求的 MVP。

### 路径 C：用户主动投喂的个人知识操作系统（推荐）

产品长在微信里（低摩擦入口），数据只来自用户带进来的内容与自己写的交往备忘。

- 优点：合规、可过审、图谱/建议可做深、和「第二大脑 / 个人 CRM」品类有参照。  
- 缺点：冷启动靠习惯；覆盖率永远不是 100% 微信行为。  
- 结论：**这是唯一同时满足原价值、平台规则和可持续经营的主路径。**

推荐理由很具体：原需求里真正难复制的不是「日志」，而是「解释 + 位置 + 建议」。解释和建议不需要全量日志，需要的是**足够密、足够真的样本**。每周 15～40 条高质量入库，已经能做出像样的周报和图谱；这比 200 条脏数据、且随时被封号更有用。

## 5. 推荐方案的设计框架

### 5.1 产品原则

1. **只处理用户带进门的东西。** 门的形状是：转发、粘贴、打卡、自己写的备忘。  
2. **人脉是用户建档，不是微信通讯录同步。** 人物节点的主键是用户创建的 ID，不是好友微信号。  
3. **时间分配承认自己是「已记录注意力」而非「真实人生」。** 所有图表脚注写清口径。  
4. **比较只在自愿样本里发生。** 默认关闭；打开时只上传匿名聚合特征。  
5. **本地可导出、可删除、可关闭云端。** 这不是文案，是信任产品。  
6. **不做聊天内容分析，包括截图 OCR。** 备忘必须是用户重新组织过的自己的话。

### 5.2 信息架构（四个工作台）

```text
今日捕获  →  图谱  →  周报  →  建议
    │         │        │        │
    └─────────┴────────┴────────┘
              设置 / 隐私 / 导出
```

**今日捕获（首页）**

- 一键：从剪贴板识别公众号 / 视频号链接并询问「要记下这篇吗？」  
- 主按钮：粘贴链接、选主题、估一个时长（1 分钟 / 5 分钟 / 20 分钟）  
- 次按钮：记一个人（姓名或备注、场合、三句备忘）  
- 今日已记：时间线，可改主题、可删  

微信里真正能用的捕获漏斗只有这几条，按转化优先级排：

1. 公众号文章右上角「转发」到本小程序（需做好分享卡片落地页：自动解析 URL、标题、公众号名）  
2. 用户复制链接后打开小程序（`onShow` + 隐私授权后的剪贴板）  
3. 订阅消息提醒「花 30 秒做今晚复盘」（三道选择题，不是打开日记本）  
4. 视频号：用户分享或粘贴后，用 `wx.openChannelsActivity` 提供「回看」，用打卡表示「看过」  

**图谱**

- 主题云：本周注意力占比  
- 来源图：公众号 / 视频号 / 其他链接 / 人物备忘  
- 人脉图：点是人，边是共同主题或互动次数  
- 内容节点：点进去是摘要、主题、关联的人  

**周报**

- 记录了多少条、覆盖几天（完整度，诚实展示）  
- 主题饼图、来源列表  
- 「你反复遇到的人」  
- 和上周比：什么变多了、什么消失了  

**建议**

- 主题缺口：你标记了「想深耕的领域」，但这周样本为 0  
- 来源过窄：80% 来自 1～2 个号  
- 关系腐烂：超过 N 天未跟进、且你自己标了「重要」  
- 拓展方向：只基于用户已选目标 + 已记录图谱，不装成全网智能

### 5.3 关键交互：把「记录」做成 10 秒动作

失败模式是做成印象笔记。成功模式是做成「下班打卡」。

**内容入库（目标 ≤ 10 秒）**

1. 识别来源类型（公众号文章 / 视频号 / 网页 / 未知）  
2. 自动填标题；失败则让用户打几个字  
3. 主题：3 个推荐 +「其他」  
4. 时长：三档，不填精确分钟  
5. 可选：关联一个已有人物  

**人物备忘（目标 ≤ 30 秒）**

- 场合（会议 / 私聊 / 群 / 线下）——用户选，系统不探测  
- 主题标签  
- 一句话：谈了什么  
- 一句话：下一步  
- 不提供「粘贴聊天记录」输入框，产品上直接拆掉这个诱惑  

**每晚复盘（目标 ≤ 30 秒，订阅消息唤起）**

三问即可：

1. 今天信息输入主要是：工作 / 行业 / 新闻 / 娱乐 / 几乎没看  
2. 有没有一个值得记下的人？有 → 跳人物卡片  
3. 有没有一篇值得留下的内容？有 → 粘贴或从最近分享进入  

这比试图 24 小时监听更接近真实用户愿意做的事。

### 5.4 「全部用户中的水平分布」怎么做才不违法、不误导

能做的：

- 用户单独打开「加入匿名比较」  
- 上传的是聚合特征，例如：本周主题向量、来源多样性指数、记录天数、人物节点数、跟进及时率  
- 不上传标题原文、人名、链接、备忘正文  
- 分位文案：`「在本产品选择比较的用户中，你的来源多样性位于前 30%」`

不能做的：

- 声称代表全体微信用户  
- 用关系链或通讯录去重「真实社交规模」  
- 把比较结果卖给第三方做广告定向（平台规范与个保法都不允许这样用）

若样本太小，就显示「样本不足」，不要编造平滑曲线。

### 5.5 建议引擎：先规则，后模型

第一版不要上「黑盒人生教练」。用可解释规则：

- 目标领域本周条目 < 2 → 建议关注 1 个该领域来源（来源由用户收藏池或编辑精选，而不是爬取微信推荐）  
- 单一来源占比 > 60% → 提示信息茧房  
- 重要人物超过 14 天无备忘 → 提醒跟进（不是去微信里偷看有没有聊天）  
- 连续三周只有新闻没有方法类内容 → 建议增加「可执行」类记录  

有了稳定标注数据之后，再在用户**已入库文本**上做个性化主题挖掘。训练数据不得混入聊天原文。

## 6. 数据模型（知识图谱最小集）

只建模你能合法拥有的对象。双向关系都要在产品层写清，避免做成「影子微信」。

```text
User 1──n CaptureEvent
User 1──n Person
User 1──n Source
User 1──n Topic
User 1──n TimeSlice (周 / 日)

CaptureEvent n──1 Source
CaptureEvent n──n Topic
CaptureEvent n──n Person
Person n──n Topic
```

建议字段（逻辑模型，不是某家 ORM 的DDL）：

**CaptureEvent（一次注意力事件）**

- id、userId、occurredAt、durationBucket  
- type：article / video / live / web / note / person_memo  
- url（用户提交）、title、sourceId  
- summary：用户自己的一句话，可空  
- 不存：聊天原文、截图、微信消息 id  

**Source**

- 用户命名的来源：某公众号名、某视频号名、某播客、某网站  
- 平台类型枚举  
- 无法从微信拉取「是否仍关注」，所以不设 `isFollowedOnWeChat`

**Person**

- displayName（用户起的备注，不必是真名）  
- context、importance、lastTouchedAt  
- 禁止字段：微信 unionid 当好友、手机号当默认主键（手机号若用于登录另说，不要用来匹配「这是不是你的微信好友」）

**Topic**

- 系统预置树（财经 > 宏观 / 公司 / 理财…；新闻；科技；职场；广告与营销；健康；教育…）  
- 用户自定义标签  
- 每条事件可多主题，但周报按主主题计

**WeeklySnapshot**

- 由事件聚合生成：主题占比、来源 HHI（集中度）、人物活跃数、完整度（7 天中有记录的天数）  
- 若用户同意比较：只把快照的数值特征送入匿名集

图谱可视化用「主题—来源—人物」三部图即可，不要一上来上力导向的万节点社交图。个人周数据通常只有几十个点，清晰比炫酷重要。

## 7. 技术架构（小程序形态）

```text
微信客户端
  小程序 UI（捕获 / 图谱 / 周报 / 设置）
       │  TLS
       ▼
  业务 API（鉴权、入库、聚合、建议规则）
       │
       ├─ 对象存储：仅用户主动提交的链接预览所需的公开元数据缓存
       ├─ 数据库：用户隔离的图谱与事件
       └─ 可选：LLM 分类（标题+用户摘要 → 主题），输出结构化 JSON

比较服务（独立库，与明文内容隔离）
  只收匿名特征向量
```

实现要点：

- **身份**：`wx.login` + 自有账号；不向用户索取微信号、密码。  
- **解析公众号链接**：只解析用户主动提交的 URL 的公开标题与账号名；不要做全站爬虫，不要绕过微信反爬去拉正文。正文不是 MVP 必需——标题 + 用户一句话足够分类。  
- **视频号**：保存用户给的视频标识，回看走官方打开接口；观看完成以用户打卡为准。  
- **剪贴板**：走隐私协议与 `wx.requirePrivacyAuthorize`；每次打开都弹「发现链接，要记下吗」，允许永久关闭自动检测。  
- **分享落地**：`onShareAppMessage` 带 contentId；从会话打开时写入一条「从分享进入」事件，这是微信允许的本应用内行为。  
- **群 openGId**：最多记「该条分享来自某匿名群」。不要试图还原群，也不要据此建关系链。  
- **存储与删除**：设置页提供导出 JSON / 删除账号；服务端按规范在终止服务后删除。  
- **主体**：个人主体能做 MVP，但视频号内嵌、部分跳转、类目与隐私接口对企业主体更稳。若认真做，用企业主体并配齐《用户隐私保护指引》。

不需要在第一期上微服务。需要在第一期就分开「用户明文」和「匿名统计」，否则以后比较功能会把隐私模型拆爆。

## 8. 合规、审核与伦理（决定能不能上线）

### 8.1 平台

对照运营规范，产品设计阶段就要消掉这些雷：

- 不收集、不要求提供好友列表、关系链、聊天记录、微信账号密码  
- 不拿本小程序数据去补全另一套社交关系链  
- 采集前明示目的、范围；隐私协议与系统隐私指引一致  
- 不诱导分享、不强制转发才能用核心功能  
- 名称、品牌不要让人误以为是腾讯官方「微信助手」  

类目建议走「工具 > 信息查询 / 笔记」或「教育 > 学习工具」中能说清「用户主动记录」的类目，不要用「社交」去碰关系链红线。以微信公众平台当次类目表为准。

### 8.2 法律（中国大陆）

- **个保法**：内容主题、阅读偏好、人脉备注都属于个人信息；通信内容是敏感个人信息。本方案用「用户自写备忘」避开通信内容，仍要告知、同意、最小必要、可撤回。  
- **比较与建议**：若对公众提供画像或推荐，评估是否需要算法备案、是否要提供不针对个人特征的选项。  
- **安全**：用户图谱一旦泄漏，伤害大于普通待办清单。按等保与最小权限做，而不是「先上线再加密」。  

### 8.3 伦理

即使合法，也不该鼓励用户把别人的对话拿来分析。产品文案应是「记下你自己的收获」，不是「监控你的社交」。周报避免羞辱性语气（「你比 90% 的人更封闭」）；比较默认关闭。

## 9. 增长、商业与竞争现实

### 9.1 获客冷知识

小程序没有系统通知权去问「你刚刚在订阅号看了什么」。获客只能靠：

- 关联公众号的内容互推（你自己要有内容能力）  
- 视频号挂载（主体条件满足时）  
- 用户把小程序转发给需要一起复盘的同事（工具属性，不是裂变游戏）  
- 搜一搜关键词：周报、知识管理、人脉、阅读记录  

最大增长瓶颈不是投放，是**记录习惯**。所以订阅消息的「每晚三问」是核心循环，不是附属功能。

### 9.2 和谁在抢注意力

- 微信自己的收藏、看一看、搜一搜：入口更原生，但不做个人图谱与建议  
- 笔记类小程序 / 印象笔记 / 飞书妙记：记录强、微信捕获弱  
- 个人 CRM（如各种人脉 App）：人脉强、但不在微信会话路径上  
- 手机系统屏幕时间：有时长，无语义、无人脉  

空隙是：**语义化的注意力账本 + 人脉备忘 + 长在微信分享路径上**。不要声称「比微信更懂你的微信」。

### 9.3 商业化（在有习惯之后）

- 免费：捕获、基础周报、本周图谱  
- 订阅：长期图谱、建议、导出、多设备  
- 不要卖用户画像  
- B 端支线（路径 B）单独品牌、单独数据边界，避免个人数据流入企业分析

## 10. 风险登记

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| 审核被判定为收集微信数据 | 无法上线 | 功能介绍、截图、隐私协议全部写成「用户主动添加」；去掉任何「同步微信记录」文案 |
| 用户记录率低，图谱空洞 | 周报不可信 | 把完整度当作一等公民；空状态教用户转发一篇文章，而不是展示空白力导向图 |
| 剪贴板被系统与用户反感 | 卸载 | 默认关闭或每次询问；提供设置 |
| LLM 把标题分错类 | 洞察荒谬 | 用户可一键纠正；纠正反馈进规则 |
| 比较功能被理解成全网排名 | 误导、投诉 | 文案锁定「本产品自愿样本」 |
| 把备忘做成聊天备份 | 违规 | 产品层禁止粘贴长对话；字数上限；不提供截图入口 |
| 主体与类目选错 | 接口与广告能力受限 | 企业主体 + 说得清的工具类目 |

## 11. 分期：按能力而不是按日历

不估「几周做完」。按依赖关系切开。每期都必须能单独上线、单独过审。

### 第 0 期 — 边界冻结

- 书面确认：不做聊天、不做好友列表、不做观看历史同步  
- 隐私协议、隐私指引、数据分类（明文 vs 匿名特征）  
- 主题树第一版（两级即可）

### 第 1 期 — 捕获闭环

- 登录、粘贴链接、手动记一条、主题与时长三档  
- 分享到小程序的落地解析  
- 时间线 + 删除 / 导出  
- 成功标准：用户能在微信里把一篇公众号文章送进时间线，并在第二天还找得到

### 第 2 期 — 周报

- 按周聚合主题与来源  
- 订阅消息唤起「今晚三问」  
- 完整度指标  
- 成功标准：有记录的用户能看懂「这周注意力去了哪」，且口径脚注存在

### 第 3 期 — 图谱与人脉

- 人物卡片与会后三句话  
- 主题—来源—人物三部图  
- 跟进提醒（只基于用户自己的日期）  
- 成功标准：用户能为真实发生的一次交流留下备忘，并在图谱里看到该人与主题相连

### 第 4 期 — 建议与自愿比较

- 规则引擎四条建议  
- 匿名分位（独立数据面）  
- 成功标准：建议能指出用户自己标过的缺口；比较可一键退出并删除特征

视频号 / 直播打卡可插在第 1～2 期，但不要阻塞公众号文章这条主漏斗——后者才是微信里最自然的转发场景。

## 12. 给决策者的建议（可直接当原则用）

1. **把口号从「还原你的微信」改成「接住你愿意留下的微信」。** 前者是平台禁区，后者是产品。  
2. **主指标不要用 DAU，用「每周至少 5 条有效捕获的用户数」和「周报打开率」。** 没有捕获，图谱是假的。  
3. **人脉模块对标个人 CRM，对标不了微信通讯录。** 谁要同步好友，谁就在写封号申请。  
4. **时间分配永远带口径。** 「已记录的 3.5 小时信息输入」可以；「你本周在微信里看了 11 小时财经」不可以。  
5. **比较功能是高级、默关、可销毁的。** 它满足原需求里的「水平分布」，但用错一句文案就会变成虚假宣传。  
6. **不要做多端 hook「补数据」的幻想。** 小程序做不成的，App 加无障碍同样不该做。差的是权限与法律，不是容器。  
7. **若商业目标其实是帮媒体理解读者，就去做路径 B，别混在个人产品里。** 数据方向相反，混在一起会把隐私模型和管理员权限一起弄脏。  
8. **先做 10 秒入库，再做图谱美化。** 可视化很便宜，习惯很贵。

## 13. 假设与未决事项

本文按以下假设写成；若假设变化，结论里只有路径 B 可能升为主路径。

- 用户是个人，要看自己的注意力与关系，而不是监视他人  
- 形态锁定微信小程序，不使用企业微信会话存档  
- 运营地区以中国大陆为主，适用个保法与微信国内运营规范  
- 不接受外挂或聊天备份导入作为 MVP  

若后续要写成实现说明书，需要单独拍板的只有三件产品事：

1. 人物备忘是否允许语音输入（仍必须是用户自己的话，且默认云端 ASR 要进隐私协议）  
2. 比较功能是否进入第一年范围（建议第 4 期再做）  
3. 主体用个人还是企业（影响视频号能力与类目）

在这三件事拍板之前，第 0～2 期已经可以按本文开工。
