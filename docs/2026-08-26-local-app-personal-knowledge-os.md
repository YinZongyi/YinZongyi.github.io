# 本地优先「个人注意力与人脉 OS」（类 Obsidian 手机 App）

## 设计框架、可行性分析与建议

> 文档日期：2026-08-26  
> 相对上一份小程序方案：形态从微信小程序改为用户设备上的本地 App；采集设想增加「录屏后提取、再删除录像」。  
> 定位：产品与架构设计备忘。不提供对微信或其他 App 的界面抓取、无障碍遍历、后台隐秘录屏等实现路径。  
> 前提：服务对象仍是用户整理**自己的**注意力与关系，而不是监视他人。

---

## 0. 结论先讲清楚

把产品从微信小程序换成「下载到手机、本地处理、类似 Obsidian」之后，**知识图谱、本地仓库、主题分类、人脉卡片、周报和建议**这一侧会立刻变得可行，而且比小程序更像一个能活十年的工具。

但「录屏 → 抽出公众号 / 视频号 / 直播 / 聊天对象与原文 → 删除录像」这一侧，**并不能因为改成本地 App 就自动合法或自动可上架**。本地处理只解决「数据先不上传云端」，不解决下面四件事：

1. **操作系统根本不让第三方长期录别的 App。** iOS 尤其如此；Android 也要求持续明示，且越来越紧。  
2. **应用商店把「读其他 App 的界面 / 通知 / 无障碍树」默认当成监控软件。** 即使用户同意、录像马上删，审核看的是能力，不是你的口号。  
3. **聊天原文里有对方的个人信息。** 用户可以同意处理自己的数据，不能单方面授权你去结构化「张三上周跟你说了什么」。  
4. **「在全部用户中的水平分布」和「纯本地、数据不出门」互相打架。** 分位一定要有一条可选的匿名网络面，否则诚实的产品就不该承诺这件事。

因此本方案的产品定义应改成：

> 一部长在用户设备上的个人知识操作系统：默认本地、文件对用户可见（类 Obsidian 仓库），用系统分享、使用时长、用户自己的备忘来建图谱；**不把常驻录屏当成读取微信人生的主引擎。**

类比要选对：Obsidian 赢在「用户写的笔记变成图」，不是「把别的 App 透明化」。更接近你原话的是桌面端的 Rewind / Microsoft Recall 一类「屏幕记忆」——它们已经在隐私与监管上反复挨打，而且主要活在电脑上，不是手机应用商店里。

## 1. 需求还原：五层价值，两个完全不同的技术问题

上一份小程序文档把需求拆成五层，这里仍然成立：注意力账本、语义理解、关系账本、时间分配、位置与建议。换成 App 之后，它们裂成两块：

| 块 | 内容 | 换成本地 App 之后 |
| --- | --- | --- |
| 块 I：知识 OS | 本地仓库、双链、图谱、周报、建议、导出 | **可行**，而且应该成为产品本体 |
| 块 II：自动还原其他 App | 录屏/无障碍还原微信内容、聊天、广告、各 App 使用细节 | **手机上作为主路径不可行**；即使用户自愿，也不应设计成默认能力 |

块 I 对标 Obsidian、Logseq、Heptabase。  
块 II 对标监控软件、家长控制越权、以及桌面端「回忆录」产品。两者叠在同一个 App 里，商店和用户都会按块 II 来审判你。

「提取后删除录像」只减少存储，不减少块 II 的本质：你已经把别的 App 里出现过的文字（包括别人说的话）写成了长期知识库。删的是 mp4，留下的是更敏感的结构化副本。

## 2. 手机系统实际给什么：不是桌面，更不是微信

### 2.1 三层墙

```text
┌─────────────────────────────────────────────┐
│  商店政策：把「读其他 App」当成间谍软件能力   │
├─────────────────────────────────────────────┤
│  操作系统沙箱：App 只能看见自己的磁盘和        │
│  用户明确授予的少数系统 API                   │
├─────────────────────────────────────────────┤
│  被观察的 App（微信等）：防截屏、反自动化、    │
│  协议禁止第三方采集                           │
└─────────────────────────────────────────────┘
```

本地计算发生在你自己的进程里，但屏幕上的像素、无障碍节点、通知正文，在系统看来属于**别的 App 和别的人**。Obsidian 从来没有去撞这三层墙，所以它能活。

### 2.2 iOS：块 II 基本没有产品化空间

| 设想 | 实际情况 |
| --- | --- |
| 后台录制微信 / 其他 App | 第三方做不到。ReplayKit 面向录制**本 App** 或用户发起的直播，不能当系统级「记忆所有屏幕」 |
| 读取其他 App 的界面文字 | 沙箱禁止。辅助功能 API 给残障辅助，商店拒绝拿它刮数据 |
| 哪些 App 用了多久 | Screen Time / Device Activity 主要给家长控制与系统设置；普通开发者拿不到「微信里看了哪篇公众号」 |
| 分享进来 | **Share Extension 是正道**：用户在微信点分享，把链接/文件送到你的仓库 |
| 常驻屏幕 OCR | 无可用、可上架的后台能力 |
| 与微信互读聊天 | 不存在 |

结论：在 iPhone 上，你的 App 可以做成很好的 Obsidian 子集 + 分享入库 + 本地模型；**不能做成「录下我用微信的一周」。** 若只做 Android、放弃 iOS，等于主动丢掉国内很大一部分知识用户，且 Android 上架仍过不去块 II。

### 2.3 Android：技术上靠近，产品上仍是死路当主引擎

Android 比 iOS 多几扇门，但门后面写的是「请证明你不是木马」：

| 能力 | 能知道什么 | 不能知道什么 | 代价 |
| --- | --- | --- | --- |
| 使用情况访问（Usage Stats） | 哪些 App 打开过、前台时长 | 微信里面看了哪个号、聊了谁 | 用户要到系统设置里单独打开；能支撑「App 时间分配」，支撑不了内容图谱 |
| 屏幕采集（用户每次授权、前台通知） | 当前屏幕像素 | 不等于稳定的公众号标题、视频号 ID、聊天气泡结构化数据 | 必须持续通知；耗电发热；支付页/部分聊天可能是黑屏；用户随时能在状态栏关掉 |
| 通知读取 | 部分推送的标题和摘要 | 不是完整聊天，也不是阅读历史 | 商店把通知监听当高危；微信通知常被折叠、脱敏 |
| 无障碍服务 | 理论上能读当前界面控件树 | 用来建内容/人脉库 = 典型的数据抓取 | 政策要求用途必须是无障碍本身；拿来抽微信会按间谍软件处理 |
| 相册 / 文件 | 用户自己保存的截图、导出文件 | 不是自动历史 | 用户主动导入才干净 |

即便只谈工程现实，用录屏当主引擎也会垮：

- 必须全天候前台服务，电池与散热不可接受。  
- 微信等应用会对敏感界面防录屏，得到的是黑帧，不是语料。  
- OCR / 多模态从视频里「还原聊天」误差大，群聊昵称、引用、表情、折叠消息会系统性脏数据。  
- 录像「提取后删除」仍要在提取窗口把帧和识别结果放进内存与临时文件，手机丢失或备份时，这是高价值目标。  
- 国内厂商 ROM 对后台、录屏、无障碍有额外限制，机型矩阵会把维护成本吃掉。

### 2.4 微信与其他内容 App 不会因为你是本地软件就合作

换容器（小程序 → App）不改变微信的商业与合规结构：阅读历史、视频号观看、直播、会话，仍是平台资产。用户协议同样不允许用自动化或外部工具去采集。本地 App 去「看见」这些界面，只是从开放接口越权，变成了系统能力越权。产品设计不应把赌注押在「微信不追究个人用户」上——应用商店会先追究开发者。

### 2.5 「全部用户中的水平」不是本地功能

纯本地 App 可以有：

- 你自己的周环比、主题占比、来源多样性、人脉跟进率  

它不能有真正的「在全部用户中的百分位」，除非：

- 用户单独打开「加入匿名比较」，并且  
- 上传的是无原文、无人名、无链接的特征向量，并且  
- 文案写成「本产品自愿样本」，不是「全体手机用户 / 全体微信用户」

若你要把「纯本地、无网络」写成卖点，就应**删掉水平分布**，或把它降级为「和你自己的过去比」。两者都写，是产品诚实性问题。

## 3. 原功能对照（本地 App 口径）

| 原功能 | 自动、常驻、录屏还原 | 本地 App 上可上架的做法 |
| --- | --- | --- |
| 访问过哪些公众号 / 视频号 / 直播 | 不可行 | 微信/浏览器分享到本 App；粘贴链接；用户点「记一笔」 |
| 使用哪些 App、时长 | **部分可行（Android Usage Stats；iOS 极弱）** | Android 做 App 级时间饼图；iOS 引导用户看系统屏幕时间，或手工估 |
| 内容领域（财经、新闻、广告…） | 没有干净语料则不可行 | 对仓库里的标题、用户摘要、本地模型分类；广告不要指望自动识别 |
| 与谁交流、沟通什么 | 不可行（且不应做） | 人物笔记：用户自己写场合、主题、下一步；可从通讯录**选一个名字**作为显示名，但不导入聊天 |
| 时间分配 | App 级可行，内容级靠记录 | 系统用量 + 每条笔记的时长分档 + 完整度 |
| 知识图谱 | 可行 | 就是产品本体：笔记 / 来源 / 主题 / 人物双链 |
| 人脉网络 | 可行（自建） | 人物页之间的边 = 共同主题与互动笔记，不是微信好友图 |
| 人群分位 | 与纯本地冲突 | 可选匿名网络面，或只做自身趋势 |
| 拓展建议 | 可行 | 规则引擎读本地图谱即可，不必上传原文 |

## 4. 三条路径，仍然只推一条主路

### 路径 A：常驻录屏 / 无障碍「微信记忆体」

用户打开一次授权，之后自动抽出本周看过的号、聊过的人、说过的话。

- 看起来最贴原需求。  
- iOS 做不到；Android 能做出演示，做不出可上架、可维持、可过法务的产品。  
- 一旦做出「沟通什么内容」，你就在处理通信内容与第三方个人信息。  
- **结论：不作为产品路径。** 本文不讨论如何实现它。

### 路径 B：桌面「屏幕记忆」+ 手机仓库（有限、可选、高风险）

在电脑上做用户明确发起的工作回顾（类似桌面回忆录），手机只当查阅端。即使如此：

- 监管与舆论成本极高（Recall 类产品已被反复证明）。  
- 默认应排除即时通讯窗口，或只保存用户自己圈选的区域。  
- 与「手机下载即用」的原话不一致，只能当远期研究，不能当 MVP。

### 路径 C：本地优先的个人知识 OS（推荐，类 Obsidian）

默认完全在设备上；仓库是用户能用文件管理器看见的 Markdown（或等价开放格式）；捕获靠分享、粘贴、打卡、语音备忘；Android 可叠加 App 使用时长；图谱、周报、建议都在本地算。

- 能上架、能跨 iOS/Android、能和 Obsidian 互导。  
- 覆盖率不是 100% 真实人生，但样本足够密时，五层价值里除「偷听聊天」外都能交付。  
- **结论：主路径。**

## 5. 推荐方案的设计框架

### 5.1 产品原则

1. **仓库属于用户。** 默认 `Documents/Vault/` 或用户选的文件夹；纯 Markdown + YAML；用户可复制到电脑用 Obsidian 打开。这是信任的根，也是与「黑盒录屏 App」的区别。  
2. **本地默认、网络可选。** 第一期可以零账号。比较功能单独开关，默认关。  
3. **捕获必须是用户能理解、能关掉、能看见状态的。** 状态栏常驻「正在记录你的微信」不可接受。  
4. **即时通讯列入默认排除。** 即便以后做「圈选当前屏幕存一张参考图」，也不对会话做文字还原。关系用人物笔记表达。  
5. **删原始媒体不等于删责任。** 任何派生文本都按个人敏感数据保护：加密、锁屏、可销毁。  
6. **时间分配承认口径。** 「已记录注意力」和「Android 的 App 前台时长」分两条曲线展示，禁止合成假的「微信内容时长」。  
7. **不做隐藏采集。** 不申请与产品故事无关的无障碍、通知监听、设备管理员。

### 5.2 和 Obsidian 对齐什么、拉开什么

对齐（不要重新发明）：

- 本地文件夹即数据库  
- 一篇笔记一个文件，双链 `[[人物/王晓]]`、`[[主题/宏观]]`  
- 图谱是链接的可视化，不是另搞一套封闭图数据库当唯一真相  
- 插件/过滤器以后再做，MVP 用固定结构

拉开（这才是你的产品）：

- **移动端捕获体验**：分享扩展、剪贴板询问、30 秒夜间复盘，比桌面 Obsidian 更适合「在微信里刚看完」  
- **周报与建议**：Obsidian 不管这件事  
- **人物 CRM 视图**：不是普通笔记列表，而是跟进、主题、最近接触  
- **Android 用量图**：和笔记图谱并排，让用户看见「时间」和「记下的内容」差多少（完整度教育）

不要做的拉开：

- 把 Obsidian 加上隐秘录屏。那不是差异化，是把一个干净品类做成高危品类。

### 5.3 信息架构

```text
收件箱 Inbox     →  日记 / 周报  →  图谱  →  建议
人物 People      →  跟进
来源 Sources     →  公众号与 App 名（用户命名）
设置             →  仓库位置、加密、用量授权、匿名比较（关）
```

文件系统建议（用户打开电脑就能认）：

```text
Vault/
  inbox/2026-08-26-mp-title.md
  daily/2026-08-26.md
  people/wang-xiao.md
  sources/caixin.md
  topics/macro.md
  weekly/2026-W34.md
```

每条内容笔记最少字段：时间、类型（文章/视频/直播/App/人物备忘）、标题、链接（可空）、主题、时长分档、来源、相关人物。没有「聊天原文」字段，也不要在 UI 上引导粘贴对话。

### 5.4 捕获漏斗（按合规与转化排序）

这是产品能否活下来的核心，比图谱算法重要。

**P0 — 系统分享（iOS Share Extension / Android Share Intent）**

用户在公众号、Safari、YouTube、甚至微信里点分享，选本 App。这是手机上唯一真正成熟的「跨 App 进仓库」方式。落地后：认链接、抽标题、猜主题、请用户确认时长。目标 10 秒。

**P0 — 剪贴板（打开 App 时询问，可永久关闭）**

发现 `mp.weixin.qq.com` 或视频号分享链，问「要记下这篇吗？」。不要后台偷读剪贴板。

**P0 — 夜间三问（本地通知，用户授权后）**

1. 今天信息输入偏：工作 / 行业 / 新闻 / 娱乐 / 几乎没有  
2. 有没有一个要记的人？  
3. 有没有一条要留的内容？  

**P1 — Android 使用情况**

单独一页「App 时间」，与知识图谱分开展示。授权文案只说「用于显示各 App 前台时长」，不说「将读取微信内容」。

**P1 — 语音备忘**

用户对自己说话：「刚和王晓聊了融资进度，下周发材料。」设备端语音转写，写成人物笔记。这是用户自己的话，不是录对方。

**P2 — 用户自己导入截图**

相册选图，本地视觉模型抽标题和大致版式，**用户确认后**才入库。默认模板按「文章卡片 / 白板 / 幻灯片」来，不为气泡对话做专用模板。即时通讯 App 的截图可以拒绝或只允许用户手打摘要。

**不进入路线图**

- 常驻屏幕录制其他 App  
- 无障碍遍历微信控件  
- 通知监听还原对话  
- 自动通讯录/好友匹配建关系链  

关于「用户主动按一个钮、录 15 秒当前屏幕、本地出标题再删视频」：即使做成显式、有倒计时、有声音或边框提示，也只适合对**非即时通讯**的内容页做辅助（例如自己的浏览器）。它不能当本周微信行为的主样本来源，也不应默认开启。即时通讯窗口应直接拒绝进入这种模式。本文到此为止，不展开识别与解析实现。

### 5.5 图谱、人脉、建议（都在本地算）

**知识图谱**  
节点：笔记、来源、主题、人物、周。边：双链与共现。周数据通常几十到几百点，手机上用三部图（主题—来源—人物）比力导向全图更清晰。

**人脉**  
每个人一篇笔记。边来自：你写过的共同主题、你标记的「介绍人」、你自己填的「最近接触」。不要读通讯录以外的关系，通讯录也只用于选显示名。

**时间分配**  
两条序列：

- 记录序列：本周入库条目的时长分档之和  
- 系统序列（仅 Android）：各 App 前台时长  

完整度 = 有记录的天数 / 7，以及「微信前台 8 小时 vs 只记了 6 条」的对照。这个对照本身就是产品：教用户分享，而不是去偷屏幕。

**建议（第一版规则，可解释）**

- 你在设置里钉过的领域，本周条目 < 2  
- 单一来源占比过高  
- 标为重要的人超过 N 天没有新笔记  
- 连续三周只有新闻没有「可执行」类笔记  

本地小模型（端侧 LLM）只做：标题主题分类、从用户自己的备忘里抽「下一步」日期。不把聊天截图当训练或推理输入。

**分位**  
默认不做。若做：独立同意、独立进程、只发数值特征、可一键删云端特征。第一年建议不做，以免污染「本地优先」叙事。

### 5.6 端侧技术架构（逻辑分层，不是实现手册）

```text
┌──────────────────────────────────────────┐
│  捕获面：分享扩展 / 粘贴 / 复盘 /（Android）用量 │
├──────────────────────────────────────────┤
│  仓库面：用户目录中的 Markdown + 附件         │
│  索引面：本地 SQLite 或等价，可随时从文件重建   │
├──────────────────────────────────────────┤
│  理解面：规则 + 可选端侧模型（主题、摘要）      │
│  洞察面：周报、图谱、建议                     │
├──────────────────────────────────────────┤
│  安全面：系统锁屏、可选仓库口令、备份加密       │
└──────────────────────────────────────────┘
可选：匿名比较通道（默认不编译进「完全离线」变体）
```

要点：

- **文件是真相，索引可重建。** 避免只有封闭数据库、用户无法迁出。  
- **分享扩展与主 App 共用同一仓库。** iOS 要用 App Group；Android 要用用户选中的目录（SAF），避免文件被系统清掉。  
- **端侧模型可选下载。** 不下载也能靠规则 + 用户点选主题工作，以免把产品绑死在大模型包体上。  
- **同步：** 第一期用系统文件/电脑数据线/用户自己的网盘文件夹；不要一上来做自建云，除非你准备好当一家同步公司。与 Obsidian 的互操作是免费的分发渠道。  
- **账号：** 可选。纯本地模式必须能用。

跨端现实：真正好用的图谱周报在平板/电脑上更舒适。合理形态是 **手机负责捕获，电脑负责回看**——这正是 Obsidian 已经验证的习惯。你的差异在手机捕获和周报，不在再做一个封闭编辑器。

## 6. 合规、上架与伦理（决定 App 能不能存在）

### 6.1 应用商店

苹果与谷歌近年都在清理：无障碍滥用、后台录屏、通知监听、跨 App 追踪。审核材料必须和真实权限一致。

- 只为「显示 App 时长」申请 Usage Stats，不要顺手申请无障碍。  
- 不要在简介写「自动整理微信聊天 / 视频号历史」。这等于告诉审核你在采集其他 App。  
- 国内安卓商店对「录屏 + 提取文字」同样敏感，且往往要求活体、加固、隐私清单与权限说明视频。

### 6.2 法律（中国大陆，用户本人场景）

- 处理阅读偏好、人脉备注，仍是个人信息；要告知、同意、最小必要、可删。  
- 通信内容属于敏感个人信息；把对话从屏幕抽成可检索文本，不能用「我录的是我的手机」一句挡掉，因为屏幕上有他人。  
- 本地存储不是免责：泄漏、备份进网盘、售后把日志带走，都仍是处理行为。  
- 「全部用户水平」若上传特征，要单独同意，禁止把特征卖去广告。

其他司法辖区还有窃听法、通信保密法一类约束。产品默认按「不做通信还原」设计，比事后按国家开开关更安全。

### 6.3 微信与第三方服务条款

即使用户安装了你的 App，用自动化手段采集微信界面仍可能违反微信软件许可。商店下架与账号风险由开发者先承担。设计上离开这条路，比准备「个人学习免责」文案有用。

### 6.4 伦理

周报避免羞辱性比较。人物笔记默认只在本机。不提供「导出某人的全部对话摘要发给第三人」这类功能。

## 7. 增长、竞争与商业

- **对标 Obsidian：** 他们已经有移动端和图谱。你必须在「从微信/浏览器进仓库的 10 秒」和「每周判断力」上明显更好，否则用户会直接用 Obsidian + 分享到文件。  
- **对标系统屏幕时间：** 他们有权威时长，没有语义。你的 Android 用量页是入口，不是产品终点。  
- **对标桌面回忆录：** 不要在手机上模仿它们的采集模型。  
- **增长：** 没有微信流量红利。靠分享扩展被用户看见、靠「可被 Obsidian 打开」降低迁移恐惧、靠周报形成习惯。主指标仍是「每周 ≥5 条有效入库」，不是安装量。  
- **商业：** 免费本地核心；付费 = 端侧更好模型、更好的人物跟进、多仓库、电脑端周报。不要卖图谱。完全离线变体可以是付费卖点。

## 8. 风险登记

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| 把录屏当卖点去宣传 | 上架失败、品牌变成监控软件 | 对外只讲本地仓库、分享入库、周报 |
| iOS 做不出「自动微信」 | 双端能力不一致 | 双端都以分享+复盘为主；用量仅 Android |
| 仓库空洞 | 图谱不可信 | 完整度作为一等公民；空状态教分享一篇文章 |
| 端侧模型把标题分错 | 周报荒谬 | 一键纠正；无模型也能手点主题 |
| 用户要求「把聊天也记上」 | 把产品拖回路径 A | 产品层引导写三句话备忘；不提供对话还原入口 |
| 自建同步泄漏 | 比笔记 App 更严重 | 第一期不自建云 |
| 同时承诺纯本地和全网分位 | 信任破产 | 分位延期或独立可选 |

## 9. 分期（按能力，不按日历）

### 第 0 期 — 边界冻结

- 书面确认：无常驻录屏、无无障碍刮界面、无聊天还原、无好友列表同步  
- 选定开放仓库格式（Markdown）与主题树  
- 隐私文案与权限清单和真实行为一致  

### 第 1 期 — 能当 Obsidian 子集用的捕获

- 本地仓库、分享入库、粘贴链接、主题与时长、日记时间线、导出整个文件夹  
- 成功标准：用户能从微信把一篇公众号分享进仓库，用电脑上的 Obsidian 打开同一文件  

### 第 2 期 — 周报习惯

- 本地周报、完整度、夜间三问、Android App 时长页（可缺省）  
- 成功标准：有记录的人能看懂「这周记下的注意力去了哪」  

### 第 3 期 — 人物与图谱

- 人物笔记、跟进、主题—来源—人物图  
- 成功标准：一次真实交流之后，用户用自己的话留下备忘并能在图上看到该人  

### 第 4 期 — 建议；分位仍默认不做

- 四条可解释规则 + 可选端侧分类模型  
- 若市场强烈要分位，再开独立同意的匿名面  

电脑端只读周报可以插在第 2 期之后，复用同一仓库，不要平行开发第二套数据模型。

## 10. 给决策者的建议

1. **先做 Obsidian 意义上的本地知识 OS，再问「还能自动多采集一点什么」。** 顺序反了，商店和法务会把整盘棋结束掉。  
2. **录屏不是本地化之后的免费升级。** 它把产品从笔记工具变成监控工具。提取后删除录像，删不掉这个分类。  
3. **聊天内容不要进入架构。** 人脉用用户自己的备忘表达，判断力足够，风险小一个数量级。  
4. **Android 的 App 时长是合法的「时间分配」切口，拿来当微信内容图谱会失望。** 让两条曲线并存，把缺口展示给用户看。  
5. **iOS 必须以分享扩展为第一公民。** 否则你没有双端产品。  
6. **和 Obsidian 互操作，不要和它为敌。** 文件兼容是信任，也是增长。  
7. **「全部用户中的水平」要么延期，要么单独同意。** 不要写在纯本地版的第一屏。  
8. **主指标仍是每周有效捕获条数。** 没有样本，图谱和建议都是装饰。

## 11. 与小程序方案的关系

| | 小程序方案 | 本本地 App 方案 |
| --- | --- | --- |
| 形态 | 微信内客人 | 系统上的独立应用 |
| 能多出来的 | 几乎没有微信侧数据 | Android App 时长；真正的本地仓库；端侧模型；与 Obsidian 互导 |
| 仍然不能做的 | 阅读历史、视频号历史、聊天、关系链 | 同样这些，外加「靠录屏假装拿到了它们」 |
| 更该做的 | 分享到小程序、夜间复盘 | 分享扩展、本地 Markdown、周报、人物笔记 |
| 建议 | 若必须活在微信里，用上一份路径 C | **若以工具为本，用这一份路径 C，优先于小程序** |

若只能做一件事：做本地 App 的第 0～2 期。小程序当可选的「分享接收器」可以以后再挂，不要反过来用小程序承载仓库。

## 12. 假设与未决事项

假设：

- 用户是在整理自己的注意力，不是观察他人设备  
- 目标平台包含 iOS 与 Android，且要上架而不是只发侧载包  
- 运营以中国大陆为主，同时不主动设计成违反商店通用间谍软件条款  
- 不做企业微信会话存档、不做 MDM 家长控制去伪装采集  

实现说明书之前只需再拍三件事：

1. 仓库格式是否严格兼容 Obsidian（建议是）  
2. 第一年是否完全不做任何云（建议是）  
3. Android 用量页是否进入第 2 期（建议进入，但与图谱分开展示）

录屏是否作为「非即时通讯、用户按一下、十几秒、强提示」的辅助入口，默认建议 **否**。它不是 MVP 的依赖，却会改写整个权限故事。若将来要重新打开，应单独立项做合规评审，而不是从本设计里长出来。
